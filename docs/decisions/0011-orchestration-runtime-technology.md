# 0011. Orchestration Runtime Technology

- Status: Accepted
- Date: 2026-06-17

## Context

ADR 0004 left the orchestration technology decision open and identified AWS Step Functions as the strongest initial candidate for an AWS-native, event-driven POC. At that point, the orchestration question was still framed broadly enough that a traditional workflow engine remained plausible.

ADR 0007 and ADR 0009 narrowed that choice substantially:

- ADR 0007 established that the Workflow Actions LLM Decision Service generates the orchestration plan rather than merely supplementing a fixed flow.
- ADR 0009 chose the hierarchical model, making Workflow Actions the top-level planner that runs first and returns a complete abstract plan for the orchestration engine to execute.
- ADR 0009 also chose a single-plan model: the plan is generated once at the start of execution, validated, and then executed faithfully.

ADR 0008 then made the execution problem more concrete by defining a transformation pipeline that includes multiple sequenced LLM and deterministic steps, plus explicit opportunities for storage and reuse of intermediate artifacts such as credential templates and mapping specifications.

Taken together, these ADRs imply a more specific requirement than "we need workflow orchestration." The system now needs a runtime that can:

- accept a structured plan generated at runtime,
- validate that plan against deterministic rules before execution,
- execute only approved step types and service actions,
- persist workflow and step state durably,
- support conditional execution, retries, timeouts, and wait/resume behavior,
- pass outputs between steps through explicit bindings, and
- produce a complete audit trail of both the generated plan and its execution.

This is not the same problem as selecting a static state-machine product. Even if an external workflow engine is used, we still need to define the generated plan schema, the service/action registry, the plan validator, the execution state model, the audit record model, and the trust boundary between LLM-generated intent and deterministic execution.

The orchestration runtime therefore needs to be chosen with two questions in mind:

1. What should be the authoritative execution model for the POC?
2. Which implementation approach gives us that model with the least unnecessary complexity?

## Decision Drivers

- Preserve the architectural intent of ADR 0009, where the Workflow Actions LLM is the top-level planner and the runtime is the faithful executor
- Keep deterministic control over which actions may be executed, how data flows between steps, and how failures are handled
- Maintain strong auditability for plan generation, validation, execution, retries, and delivery outcomes
- Stay compatible with the project's Python-first architecture from ADR 0003
- Keep the POC small enough to implement quickly without introducing a large workflow platform that we must also learn and operate
- Leave a migration path to a stronger durable workflow platform if the custom runtime proves too limited

## Decision

For the initial POC, we will implement a **project-internal orchestration service** as the primary orchestration runtime and plan executor.

This service will be the authoritative runtime for the abstract plans generated by the Workflow Actions LLM Decision Service. It will:

- look up reusable validated plans when applicable,
- invoke Workflow Actions when no reusable plan applies,
- submit generated or reused plans to the Policy Rules Service for validation,
- persist execution state,
- execute validated plan steps against a versioned registry of approved actions,
- manage retries, timeouts, waits, and resumptions,
- record complete audit traces, and
- terminate workflows with deterministic outcome states.

`AWS Step Functions` will **not** be used as the primary orchestration engine for plan execution in this POC. It may still be used at the edges as infrastructure plumbing if helpful, but it will not be the authoritative workflow definition or execution model.

Among external alternatives, the current ranking for this architecture is:

1. `Temporal`
2. `Conductor`
3. `Camunda`
4. `AWS Step Functions`
5. `Dagster` or `Airflow`

`Temporal` is the strongest revisit candidate if the project later decides that the internal runtime is providing too little durability, visibility, or long-running workflow support for the engineering cost of maintaining it. If that happens, the migration target should be a Temporal-hosted implementation of the same abstract plan contract rather than a redesign of the orchestration model itself.

## Options Considered

| Option | Description | Main concern |
| --- | --- | --- |
| Project-internal orchestration service on AWS primitives (chosen) | Build a lightweight Python plan executor using standard infrastructure such as queues, schedulers, and persistent state | We must own workflow state, retries, idempotency, and audit behavior instead of delegating them to a workflow product |
| Temporal-backed generic plan interpreter | Implement the same abstract plan contract, but run it inside Temporal workflows and activities | Temporal provides durable execution, but we would still need to design the generated plan schema, service registry, validation model, and generic interpreter; it also introduces a new workflow platform to deploy and learn |
| Conductor-backed generic plan interpreter | Map the abstract plan into Conductor workflow and task constructs | Conductor is viable and closer than BPMN-centric tools because it has explicit task definitions, expressions over workflow/task data, and wait/human/system-task primitives, but it still introduces its own workflow-definition model that our runtime would have to target |
| Camunda-backed generic plan interpreter | Map the abstract plan into Camunda BPMN processes, service tasks, events, and job workers | Camunda is strong for visual collaboration and human-readable process diagrams, but BPMN plus FEEL/Zeebe job-worker concepts is farther from our generated-plan contract than Temporal or Conductor and would require a more opinionated translation layer |
| AWS Step Functions as primary executor | Represent the workflow directly as a Step Functions state machine and fit Workflow Actions output into that model | Step Functions workflows are defined in Amazon States Language ahead of time; using it as the primary runtime would require pre-enumerating the workflow structure or embedding a custom executor inside a task, which means Step Functions would not actually be executing the LLM-generated plan |
| Dagster or Airflow | Use a broader orchestration platform already considered in ADR 0004 | Better fit for data pipelines, scheduled DAGs, and broader operational workflows than for this event-driven, runtime-planned execution model |

## Why Not Step Functions

ADR 0004 correctly identified Step Functions as a strong general-purpose AWS orchestration service. That remains true. The issue is not that Step Functions is weak; the issue is that ADR 0009 changed what "the orchestrator" must actually do.

AWS documents Step Functions as a service for building workflows from states in a state machine, defined in Amazon States Language. That is a good fit when the workflow structure is known ahead of time, even if choices inside it depend on runtime data. It is a poor fit when the workflow structure itself is generated at runtime by a planner and must then be executed as generated.

There are only two practical ways to force the ADR 0009 model into Step Functions:

1. Pre-enumerate a sufficiently broad static state machine and let the LLM only fill in branches or parameters.
2. Put a custom plan executor inside Lambda or another task and have Step Functions invoke it.

The first option effectively collapses the architecture back toward a fixed workflow with LLM-authored hints, which conflicts with ADR 0009. The second option keeps the real orchestration logic in our code anyway, meaning Step Functions becomes a wrapper around the thing we still had to build.

For this POC, that extra layer is not worth the conceptual distortion or the implementation overhead.

## Why a Project-Internal Orchestration Service

### The real design problem is the plan contract, not the outer workflow product

Once the Workflow Actions service generates a plan at runtime, the hard architectural work shifts to:

- defining the plan schema,
- defining the allowed action catalog,
- validating generated plans deterministically,
- binding step outputs into later inputs,
- deciding how conditions are expressed,
- handling retries and wait states safely, and
- auditing the full execution.

No external workflow product removes those responsibilities. At best, it provides a more durable host for them.

### The POC benefits from a narrow, explicit runtime

The POC is trying to learn whether LLM-generated orchestration plans are useful, validatable, and executable. A small internal runtime makes that research boundary explicit:

- the LLM generates an abstract plan,
- the Policy Rules Service approves or rejects it,
- the runtime executes only approved actions, and
- the audit log captures the exact plan and outcome.

This keeps the experiment focused on the actual unknowns rather than on the semantics of a third-party workflow engine.

### The custom runtime can stay intentionally small

The POC requirements explicitly exclude complex workflow branching and advanced exception handling. That matters. We do not need to build a general-purpose orchestration platform. We need a constrained plan executor for a closed catalog of actions.

That allows the implementation to stay small if we enforce the following limits:

- single generated plan per execution,
- ordered step list rather than arbitrary graph rewriting,
- bounded condition evaluation,
- closed action registry,
- no arbitrary code execution from the plan,
- exact-match plan reuse only in the initial version, and
- no mid-flight replanning in v1.

### Temporal is a good future host, but not required yet

Temporal is the strongest alternative because it is code-first, durable, supports Python, and includes the core mechanics we would otherwise have to reimplement again later for longer-running workflows. But adopting Temporal now still requires us to build the same abstract-plan interpreter and policy-validation boundary on top of it. For a POC, that means taking on a new platform without eliminating the central design work.

The correct first move is therefore to define and prove the abstract plan contract in a small internal runtime. If that contract proves valuable and the runtime's durability burden grows, Temporal is the natural next place to host it.

### Why Temporal ranks above Conductor and Camunda

`Temporal` ranks highest among external options because its core workflow model is code-first and Python is a first-class SDK language for this project. Temporal documents workflows as code, executed durably with replay and event history. That is a closer fit for a Python-first team that may eventually want to host a generic interpreter in normal application code rather than translate plans into a separate graphical or JSON-native definition language.

`Conductor` ranks next because it is also a credible fit for dynamic orchestration problems. Its official documentation shows workflow definitions composed from task configurations, input/output expressions over workflow and task data, and built-in wait, human, and other system-task/operator concepts. That is meaningfully closer to this ADR's abstract step model than Step Functions or BPMN-centric tools. However, it still asks us to target Conductor's workflow-definition model rather than execute our own plan contract directly.

`Camunda` ranks below Conductor not because it is weak, but because its strongest differentiator is also its main mismatch here. Camunda's BPMN modeler and job-worker runtime are compelling when the process diagram itself is a first-class artifact for business and technical collaboration. For this architecture, though, the first-class artifact is the LLM-generated abstract plan. Translating that plan into BPMN service tasks, gateways, events, and FEEL expressions is possible, but it is a larger semantic mapping step than targeting Temporal activities or Conductor-style tasks.

## Recommended Implementation Details

The orchestration service should be documented and implemented as a **constrained plan executor**, not as a general workflow authoring platform.

### 1. Runtime Responsibilities

The service should own the following deterministic responsibilities:

- event idempotency and workflow creation,
- execution context assembly handoff to the Context Builder,
- plan cache lookup,
- Workflow Actions invocation when required,
- plan schema validation,
- Policy Rules validation,
- step scheduling and dispatch,
- step output persistence,
- retry and timeout handling,
- wait/resume behavior,
- workflow completion or failure determination, and
- audit log emission.

These responsibilities should not be delegated to the Workflow Actions LLM.

`Event idempotency and workflow creation` means the ingress layer must decide, deterministically, what to do when the same source event is delivered more than once. In practice this means:

- deriving or receiving a stable event identity,
- checking whether that event has already produced a workflow execution,
- suppressing creation of duplicate workflows for the same event,
- and creating the initial workflow record, correlation identifiers, and starting state when the event is new.

This keeps duplicate message delivery, replay, and resume behavior out of the LLM layer.

### 2. Recommended Runtime Shape

The recommended implementation is a queue-driven orchestration runtime rather than a single long-lived in-memory process.

At minimum, it should have these logical parts:

- an ingress component that receives events, enforces idempotency, and creates the workflow record,
- a planner worker that assembles context, looks up reusable plans, invokes Workflow Actions when needed, and submits the resulting plan for validation,
- an executor worker that advances one ready step at a time and persists the result after every step transition,
- a scheduler or resume mechanism that can wake waiting workflows back up after a delay or external signal,
- adapter implementations for approved actions such as Delivery Targets, Transformation Mappings phases, policy checks, and downstream delivery calls,
- and persistent stores for workflow state, plan cache entries, and audit records.

This shape keeps the runtime stateless between worker invocations and makes retries, resume behavior, and crash recovery easier to reason about than a process-local execution model.

The validation pipeline should also be explicit:

1. schema validation of the generated plan,
2. registry validation that all referenced actions and bindings are allowed,
3. Policy Rules validation of the full plan,
4. execution only after all prior validations pass.

### 3. Versioned Action Registry

The runtime should execute only actions from a versioned registry that the orchestration service owns.

Each action definition should include at minimum:

- `action_id`
- human-readable description exposed to the Workflow Actions prompt
- implementation target or adapter binding
- input schema
- output schema
- idempotency requirements
- default timeout
- default retry policy
- whether the action is side-effecting
- whether the action may be used inside iteration

The Workflow Actions service should receive a prompt-time view of this registry. The Policy Rules Service should validate plans against the same registry version.

The LLM must never choose raw URLs, Lambda names, queue names, credentials, or arbitrary code to run.

### 4. Plan Shape

For the POC, the plan schema should be intentionally limited and **executor-neutral**.

The Workflow Actions LLM Decision Service should generate a declarative abstract plan, not Python source code, Temporal workflow code, Conductor workflow JSON, Camunda BPMN, or any other engine-specific artifact.

That is deliberate. The generated plan is the architecture's intermediate representation. It is what the Policy Rules Service validates and what the runtime executes. If the hosting technology changes later, the plan contract should remain stable while only the executor implementation changes.

The step schema should therefore align to concepts that map cleanly across plausible runtimes without adopting any one runtime's syntax as the canonical contract. For example:

- `call` maps naturally to an internal adapter invocation, a Temporal activity, a Conductor task, or a Camunda service task plus worker
- `wait` maps naturally to an internal scheduler wait, a Temporal timer or signal wait, a Conductor wait task, or a Camunda timer/message wait
- `terminate` maps naturally to workflow completion or explicit early termination in any of those runtimes

This ADR therefore does **not** preclude a later Temporal migration. It does the opposite: it preserves that option by keeping the plan portable.

If the project later adopts Temporal, the expected implementation is not "have the LLM emit Python." It is "keep the same abstract plan schema and execute it inside a Temporal-hosted interpreter whose activities correspond to the action registry."

At minimum, a plan should include:

- `plan_schema_version`
- `plan_id`
- `generated_at`
- `generator`
  - Workflow Actions service version
  - model identifier
  - prompt/template version
- `applicability`
  - event type
  - source system
  - policy version
  - action-registry version
- `confidence`
- `rationale`
- ordered `steps`

Each step should include at minimum:

- `step_id`
- `kind`
  - `call`
  - `wait`
  - `for_each`
  - `terminate`
- `action_id` for `call` steps
- `condition`
- `inputs`
- `produces`
- `timeout`
- `retry_policy`
- `on_failure`
- `metadata`
  - human-readable purpose
  - audit tags

The POC should prefer an ordered step list with explicit conditions over a free-form graph structure. A single bounded `for_each` primitive is sufficient to support per-target delivery after the Delivery Targets service resolves an actual target list.

### 5. Data Binding and Conditions

The plan must use a deterministic declarative mechanism for:

- selecting data from the execution context,
- binding prior step outputs into later inputs, and
- evaluating boolean conditions.

The implementation should not allow arbitrary Python or JavaScript execution in generated plans.

This detail should be documented explicitly:

- which expression language is used,
- what subset is allowed,
- how expressions are validated,
- how missing values are handled, and
- whether the same language is used for both input binding and conditions.

### 6. Execution State Model

The orchestration service should persist both workflow-level and step-level state.

Workflow state should distinguish at least:

- `received`
- `planning`
- `plan_validating`
- `ready`
- `running`
- `waiting`
- `completed`
- `rejected`
- `failed`

Step state should distinguish at least:

- `pending`
- `running`
- `succeeded`
- `skipped`
- `retry_scheduled`
- `timed_out`
- `failed`

The execution store should preserve attempt counts, timestamps, inputs, outputs, and failure details for every step.

If step outputs can become large, the implementation should document when outputs are stored inline in workflow state versus out-of-line in object storage with references recorded in the execution store.

### 7. Failure, Retry, and Wait Semantics

Failure behavior must be deterministic and explicit per step.

For the POC, the runtime should support only a small set of step failure outcomes:

- retry according to policy,
- fail the workflow,
- terminate early with a named business outcome,
- or mark the workflow as waiting for a later retry/resume trigger.

This is sufficient for scenarios already identified in ADR 0009 such as badge-acceptance checks, early termination for failing grades, or conditional non-delivery for sub-competencies.

### 8. Plan Reuse

Plan reuse should be conservative in the initial implementation.

The service should:

- store only plans that have already passed Policy Rules validation,
- reuse them only by exact applicability-key match in v1,
- re-submit reused plans to Policy Rules validation before execution, and
- record whether execution used a generated plan or a reused plan.

The applicability key should be documented explicitly. At minimum it should account for:

- event type,
- source system,
- policy version,
- action-registry version,
- and any context dimensions that materially affect which steps are valid.

Approximate or fuzzy plan matching is out of scope for the POC.

### 9. Audit and Trace Model

The orchestration service should record enough detail to reconstruct both the decision and the execution.

At minimum, the audit record should include:

- event identifier
- workflow execution identifier
- correlation identifier
- selected or generated plan identifier
- plan schema version
- Workflow Actions model and prompt version
- plan confidence and rationale
- Policy Rules validation result
- per-step inputs, outputs, attempts, timings, and outcomes
- downstream delivery results
- final workflow outcome

### 10. Boundaries and Non-Goals

The implementation should document what the orchestration service does **not** do in the POC:

- it does not let the LLM invent new executable actions at runtime,
- it does not support arbitrary loops or graph mutation,
- it does not do mid-flight replanning in v1,
- it does not replace the Policy Rules Service,
- it does not act as a general scheduler for unrelated jobs, and
- it does not become the repository's long-term abstraction over every possible workflow engine yet.

## Consequences

### Positive

- The runtime is aligned with ADR 0009's dynamic hierarchical planning model instead of forcing that model back into a static state machine
- The plan contract, action registry, validation boundary, and audit record become first-class artifacts of the architecture
- The POC can stay Python-first and event-driven without introducing a large new workflow platform
- The design remains portable enough to move onto Temporal later if durability or long-running workflow needs justify it

### Negative

- We must implement and maintain our own execution-state, retry, idempotency, and wait/resume behavior
- The internal runtime will initially have fewer built-in operational features than a mature workflow platform
- If the POC quickly expands into longer-running or more highly concurrent workflows, the custom runtime may become a temporary solution that later needs to be re-hosted

### Revisit Triggers

This decision should be revisited if:

- workflows become long-running enough that timers, resumptions, and recovery semantics dominate implementation effort,
- the runtime needs richer concurrency, child-workflow, or signaling semantics than the constrained executor model supports cleanly,
- audit and visibility requirements grow beyond what the internal runtime can provide economically,
- or the engineering burden of maintaining durable execution mechanics exceeds the cost of adopting Temporal or another durable workflow platform.

## Open Questions

- What concrete persistence backend should hold workflow state, plan cache entries, and audit records in the POC?
- What expression language should be used for input binding and conditions, and should that be the same language used elsewhere in the architecture?
- Should per-target delivery inside `for_each` execute serially or with bounded parallelism in the POC?
- Do we need true callback-based waits in the POC, or is scheduled retry/polling sufficient for the event scenarios we will actually demo?
- What exact context dimensions belong in the plan applicability key for reuse?
